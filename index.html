Case Study: LAAD

A production-grade ATM log aggregation, anomaly detection and diagnostics platform built for NCR Atleos.

The Problem

NCR Atleos ATMs generate MBs of log data each day across several sources, application logs, hardware sensor metrics, terminal handler logs, Kafka, Prometheus, Windows OS and GCP cloud metrics. Field engineers are flying blind: faults surface only after customers report them, and root-causing a single ATM meant grepping millions of unstructured lines by hand.

My Role, Solo Builder

LAAD began as part of a 7-person university team project. After the module ended, I continued developing it independently throughout the summer and substantially rebuilt the system. The original submission had basic rule-based detection and a simple database-writing generator, the majority of the current architecture was designed, implemented and deployed by me alone.

  • 2.5M events processed end-to-end at ~100 messages/second with zero loss
  • 99.8% ± 0.1% cross-validated accuracy on the XGBoost detection ensemble
  • 0.708 context recall from the agentic RAG assistant, 2× the deterministic baseline

Pipeline & Architecture

Seven heterogeneous sources stream into a continuous Kafka producer (gzip, acks=all, retries 5), land on two KRaft topics with 7-day retention, and are consumed by a pipeline that deduplicates, parses, dual-writes to PostgreSQL and a ChromaDB vector store, and feeds a detection engine every 30 seconds, surfaced through a FastAPI backend and a React dashboard.

  • Ingestion, Kafka KRaft, 2 topics × 3 partitions, ~65% gzip compression (250KB/s → 85KB/s on the wire), 3.5GB/day → 1.2GB/day on disk
  • Reliability, dedup via Redis SET + 10K in-memory LRU, manual offset commits, failed messages land on a Redis Stream DLQ with exponential backoff (5s → 10s → 20s)
  • Schema-on-read storage, PostgreSQL 16 with JSONB payloads: adding a new source means adding a parser, never a migration. 10 tables, 3 views, 14 indexes, hourly retention cleanup
  • Vector store, ChromaDB with semantic chunking and local 768-dim embeddings for the RAG assistant
  • API, FastAPI, 30 endpoints across 6 routers, JWT auth and 8 Redis patterns (rate limiting, caching, locks, Pub/Sub, DLQ) with graceful degradation

End-to-end flow: 7 log sources → Kafka → 3-layer detection → API → React dashboard

The 3-Layer Detection Engine

Layer 1, ML Ensemble

  • XGBoost: 49 engineered features in 7 groups, 8 anomaly classes, 99.8% ± 0.1% stratified CV accuracy
  • Isolation Forest on the 46 highest-importance features: AUC-ROC 0.9502, 97.3% precision, Youden's-J threshold from a 200-point sweep
  • Known faults at confidence ≥ 0.70; novel patterns flagged as UNKNOWN

Layer 2, Statistical Drift

  • Rolling 20-window median/std baseline; alert on |z| > 3.0
  • Catches concept drift and unseen behaviours with zero model dependency
  • Confidence from the z-score magnitude, no training data required

Layer 3, Heuristic Rules

  • 7 deterministic detectors (A1–A7): network timeouts, cash cassette faults, JVM memory leaks, container restarts, response spikes, OS memory pressure, out-of-order Kafka
  • 10-minute dedup window per (anomaly type, ATM)
  • A live SageMaker champion endpoint cross-checks predictions without overriding them

All 3 layers in action: ML ensemble, z-score drift and heuristic alerts surfacing in the anomaly list

Agentic Hybrid RAG

A LangGraph agent with 12 MCP tools answers operator questions over the anomaly corpus: ChromaDB retrieval with metadata filters and temporal decay, cross-encoder reranking, then a 4-stage reasoning loop, self-consistency sampling, verbalised confidence, reflexion and citation grounding, fused into a single score (0.30 retrieval + 0.25 self-consistency + 0.25 verbalised + 0.20 grounding) and Platt-calibrated on real feedback.
